# /매트릭스 - Phase 1.5: 소스 교차 분석 + 커버리지 매트릭스 생성

실행 옵션: $ARGUMENTS
(예: 전체(기본), 영역지정:{영역명}, 갱신)

## 목적

1. 4개 소스를 **교차 비교**하여 소스 간 불일치·누락을 식별하고, 이를 추가 TC의 원천으로 활용합니다.
2. AI가 TC를 생성할 때 **대표 표본만 쓰고 임의로 중단하는 문제**를 방지하기 위한 외부 기준점을 생성합니다.

이 두 가지가 함께 작동하여 **수량 제한 없이 풍부한 TC와 높은 커버리지**를 확보합니다.
- 교차 분석 → 개별 소스만 보면 발견할 수 없는 TC를 추가 확보
- 커버리지 매트릭스 → 수치 목표가 AI의 임의 중단을 방지

## 전제 조건

- `_summaries/` 폴더에 요약 파일이 최소 1개 이상 존재해야 합니다
- 4종 모두 있을 때 가장 완전한 교차 분석과 매트릭스가 생성됩니다
- 요약 파일이 없으면 `/소스분석 all` 먼저 실행을 안내합니다

## 실행 절차

### Step 1: 요약 파일 로드
1. `_summaries/` 폴더의 요약 파일 4종을 모두 읽기
   - `confluence_summary.md` (기능 요구사항, 비즈니스 로직)
   - `jira_summary.md` (구현 범위, 변경 사항)
   - `figma_summary.md` (UI 컴포넌트, 인터랙션, 입력 필드)
   - `code_summary.md` (변경 파일, 테스트 영향도)
2. 각 요약의 "테스트 차원 열거" 섹션을 우선 참조 (없으면 본문에서 추출)

### Step 2: 소스 간 교차 분석
4개 소스를 **6쌍**으로 교차 비교하여 불일치·누락·추가 항목을 식별합니다.

#### 2-1. 비교 대상 6쌍
| # | 소스 A | 소스 B | 주요 비교 관점 |
|---|--------|--------|---------------|
| 1 | Confluence (기획) | Figma (UI) | 기획 요구사항이 UI에 반영되었는가? UI에만 있는 요소는? |
| 2 | Confluence (기획) | Code (구현) | 기획 분기/로직이 코드에 구현되었는가? 코드에만 있는 로직은? |
| 3 | Confluence (기획) | Jira (개발범위) | 기획 변경이 개발 이슈에 반영되었는가? 누락된 Task는? |
| 4 | Figma (UI) | Code (구현) | UI 컴포넌트/인터랙션이 코드에 구현되었는가? 코드에만 있는 UI 로직은? |
| 5 | Figma (UI) | Jira (개발범위) | 디자인 변경이 개발 범위에 포함되었는가? |
| 6 | Jira (개발범위) | Code (구현) | Jira 완료 Task가 실제 코드에 반영되었는가? 코드에 있으나 Jira에 없는 변경은? |

#### 2-2. 각 쌍별 비교 항목
각 쌍에 대해 다음을 식별:

**불일치 (Discrepancy)**: 양쪽에 모두 있으나 내용이 다른 항목
- 예: 기획서에는 필수 필드인데 UI에 검증이 없음
- 예: 기획서의 에러 메시지와 코드의 에러 메시지가 다름

**누락 (Missing)**: 한쪽에만 있고 다른 쪽에 없는 항목
- 예: 기획서에 정의된 분기 조건이 코드에 구현되지 않음
- 예: Jira에 완료된 Task의 기능이 Figma에 반영되지 않음

**추가 (Extra)**: 특정 소스에만 존재하는 독자적 항목
- 예: 코드에만 있는 방어적 에러 처리 로직
- 예: UI에만 있는 추가 인터랙션 (hover, 애니메이션 등)

#### 2-3. 비교 결과 기록
각 발견 항목을 다음 형태로 기록:

| ID | 비교 쌍 | 유형 | 항목 | 소스 A 내용 | 소스 B 내용 | TC 영향 | 리스크 | 분류 근거 |
|----|---------|------|------|------------|------------|---------|--------|----------|
| CA-001 | 기획↔UI | 불일치 | {항목명} | {A의 내용} | {B의 내용} | 검증 필요 | 높음/중간/낮음 | {2-3b 기준 중 해당 항목} |
| CA-002 | 기획↔코드 | 누락 | {항목명} | {A의 내용} | (없음) | 구현 누락 or 기획 변경 확인 | 높음/중간/낮음 | {2-3b 기준 중 해당 항목} |

#### 2-3b. 리스크 정량 분류 기준

| 리스크 | 분류 기준 (하나라도 해당하면 배정) | TC 반영 |
|--------|----------------------------------|---------|
| 높음 | 사용자 직접 인지 기능 차이 / 데이터 유실·보안 위협 / 매출·결제 영향 | 반드시 TC 작성 |
| 중간 | 내부 동작 차이 / 비기능 품질 영향 / 우회 가능하나 UX 저하 | TC 작성 권장 |
| 낮음 | 문서 수준 불일치(동작 영향 없음) / 스타일 차이(기능 무관) | TC 생략 시 사유 기록 필수 |

제약 조건:
- "낮음"이 전체 발견의 20% 초과 불가. 초과 시 재검토하여 "중간" 상향 또는 근거 구체화
- 분류 모호 시 상위 등급 배정 (높음 > 중간 > 낮음)
- 교차 분석 결과 테이블(2-3)에 "분류 근거" 컬럼 추가

#### 2-4. 교차 분석 결과 저장
`_summaries/cross_analysis.md`에 저장합니다. (출력 형식 섹션 참조)

### Step 3: 기능 영역 식별
1. 요약 파일들과 **교차 분석 결과**를 함께 고려하여 **독립적인 기능 영역**을 식별
2. 각 영역에 대해 다음을 정의:
   - 영역명
   - 관련 소스 (어떤 요약 파일에서 도출되었는지)
   - 핵심 기능 목록
   - 해당 영역의 교차 분석 발견 사항 (Step 2에서 식별된 것)

### Step 4: 테스트 차원 열거 (영역별)
각 기능 영역에 대해 다음 차원을 **빠짐없이** 열거:

#### 4-1. 입력값 차원
| 필드명 | 유효값 목록 | 무효값 목록 | 경계값 |
|--------|------------|------------|--------|

#### 4-2. 사용자/상태 차원
| 차원 | 가능한 값들 |
|------|------------|
| 사용자 유형 | (프로젝트에 맞게 정의) |
| 플랫폼 | iOS, Android, Web |
| ... | ... |

#### 4-3. 분기 조건 차원
| 조건 | 가능한 값들 | 출처 |
|------|------------|------|

#### 4-4. 상태 전이 차원
| 상태명 | 전이 가능 상태 | 전이 조건 |
|--------|---------------|-----------|

#### 4-5. 교차 분석 발견 차원
교차 분석에서 식별된 불일치·누락 항목을 추가 테스트 차원으로 포함:
| 교차 분석 ID | 비교 쌍 | 유형 | 테스트 필요 사항 |
|-------------|---------|------|-----------------|

#### 4-6. 품질 특성 차원 (ISO/IEC 25010 갭 체크)
`기준_시트분류.md`의 품질 특성 커버리지 맵을 참조하여, 아래 특성이 누락되지 않았는지 체크합니다:

| 품질 특성 | 체크 관점 | 대상 시트 |
|-----------|----------|----------|
| 사용성: 학습성 | 첫 사용자 안내, 레이블 명확성, 도움말 가시성 | 명세기반 |
| 사용성: 조작성 | 키보드 인터랙션, 터치 영역, 로딩 피드백, 스크롤 연동 | 명세기반 |
| 사용성: 접근성 | 스크린 리더, 색상 대비, 포커스 관리, 키보드 탐색 | 명세기반+Regression |
| 보안 | 토큰 보안, 개인정보 마스킹, CSRF, 파일 위장 업로드 | 예외사항+코드영향도 |
| 성능 효율성 | API 응답 시간, 모달 열림 지연, 첨부 업로드, 메모리 | 코드영향도 |
| 신뢰성: 복구성 | 네트워크 복구 흐름, 브라우저 크래시 복구, 부분 제출 복구 | 예외사항+유즈케이스 |
| 사용 품질 | E2E 과업 완료, 정보 표시 정확성, 다국어 완결 흐름 | 유즈케이스 |
| 이식성: 적응성 | iOS/Android/Web/MO Web 간 일관성 | Regression |

각 특성에 대해 **최소 3개 이상 TC가 매트릭스에 존재하는지** 확인하고, 부족한 특성은 해당 영역에 조합 행을 추가합니다.

### Step 4-CT: 3단계 카테고리 트리 작성 (영역별)

`기준_실행단위분해.md` A4 규칙을 참조하여 각 기능 영역의 카테고리 트리를 작성합니다.

1. 소스(Figma UI 구조, Confluence 기능 목록, Jira Epic→Task 계층)에서 3단계 카테고리 추출
2. 각 3차 카테고리별 예상 TC 수 산정 (A1 원자적 분해 고려)
3. 플랫폼 분리 여부(A3)와 컨텍스트 복제 여부(A2)를 카테고리별로 태깅

#### 출력 형식

```markdown
### 카테고리 트리 (이 영역)

| 1차 | 2차 | 3차 | 예상 TC 수 | 플랫폼 분리 | 컨텍스트 복제 |
|-----|-----|-----|-----------|------------|-------------|
| {탭/섹션} | {기능 영역} | {세부 항목} | {N} | Y/N | Y/N ({M} 컨텍스트) |
```

#### 카테고리 완전성 검증
- 모든 3차 카테고리에 예상 TC 수 ≥ 1
- Figma 화면 구조의 모든 영역이 카테고리 트리에 포함되었는지 확인
- 카테고리 트리의 3차 항목 합계와 매트릭스 조합 행 수 비교

### Step 4-CR: 컨텍스트 복제 식별 (영역별)

`기준_실행단위분해.md` A2 규칙을 참조하여 공통 기능의 노출 컨텍스트를 식별합니다.

1. 공통 기능 목록 작성 (댓글, 공유하기, 팔로우, 좋아요, 신고하기, 새소식, 추천 프로젝트 등)
2. 각 공통 기능이 노출되는 **모든 페이지/컨텍스트** 나열
3. 컨텍스트별 차이점 식별 (있는 탭, 없는 탭, 다른 레이아웃 등)
4. 조합 테이블에 "페이지 컨텍스트" 차원 추가

#### 출력 형식

```markdown
### 컨텍스트 복제 목록 (이 영역)

| 공통 기능 | 노출 컨텍스트 | 컨텍스트 수 | 컨텍스트별 차이 |
|----------|-------------|-----------|---------------|
| 댓글 | 펀딩 상세 News, 프리오더 상세 News, Community | 3 | Community는 대댓글 불가 |
| 공유하기 | 펀딩 상세, 프리오더 상세, 오픈예정 상세 | 3 | 차이 없음 |
```

#### 복제 계수 산출
- A2 승수 = 1 + (공통 기능 TC 비율 × (평균 노출 페이지 수 - 1))

### Step 4-PUI: 플랫폼 UI 강제 분리 식별 (영역별)

`기준_실행단위분해.md` A3 규칙을 참조하여 PC/Mobile 간 UI 차이를 식별합니다.

1. Figma에서 PC 화면과 Mobile 화면의 UI 구성을 비교
2. 차이가 있는 기능을 "플랫폼 UI 분리 대상"으로 태깅
3. 조합 테이블에서 해당 기능의 플랫폼 차원을 PC/Mobile로 분리

#### UI 차이 유형
| 유형 | 판정 기준 | 예시 |
|------|----------|------|
| 노출 요소 차이 | PC/Mobile에 서로 다른 UI 요소 | PC: GNB 5개 항목 vs Mobile: 하단 네비 4개 항목 |
| 레이아웃 차이 | 같은 요소가 다른 위치/구조 | PC: 우측 고정 리워드 vs Mobile: Rewards 탭 |
| 인터랙션 차이 | 동작 방식이 다름 | PC: hover 툴팁 vs Mobile: tap 모달 |
| 한쪽 전용 | 한 플랫폼에만 존재 | PC only: 사이드바, Mobile only: 하단 GNB |

#### 출력 형식

```markdown
### 플랫폼 UI 분리 대상 (이 영역)

| ID | 기능 | 플랫폼 | UI 차이 내용 | 대상 시트 |
|----|------|--------|-------------|----------|
| PUI-001 | 네비게이션 | PC | wadiz타이틀, 국가선택, 위시, Login, Sign Up | 명세기반 |
| PUI-002 | 네비게이션 | Mobile | 뒤로가기, 국가선택, 위시, 홈버튼 | 명세기반 |
```

#### 분리 계수 산출
- A3 승수 = 1 + (플랫폼 UI 분리 대상 비율 × 0.5)

### Step 4-US: 유저스토리 차원 열거 (영역별)

`기준_유저스토리.md`를 참조하여 기존 차원을 **사용자 행동 관점**으로 재분류합니다.

1. 기존 차원(분기 조건, 화면 상태, 인터랙션)에서 사용자 상태/상황/행동을 3축으로 분리 추출
2. 3축 테이블에 프로젝트별 값 채우기

| 축 | 추출 소스 |
|----|----------|
| 사용자 상태 (State) | 분기 조건 열거 → 인증 상태, 사용자 유형, 이력 조건, 세션 상태 |
| 사용자 상황 (Situation) | 화면 상태/진입 경로 → 진입 경로, 화면 상태, 환경 조건, 시간 조건 |
| 사용자 행동 (Action) | 인터랙션/사용자 흐름 → 직접 행동, 간접 행동, 중단/이탈, 전환 행동 |

3. **동작 차별성 기준**으로 유의미한 조합만 선택: "이 상태/상황이 바뀌면 기대결과가 달라지는가?"
3-b. **조합 하한선 검증**: 최소 유저스토리 수 = max(7, ceil(3축 전체 값 수 / 3)). 미달 시 리스크 상위 조합 추가
3-c. **Pairwise 보완**: 리스크 최상위 3개 차원 간 모든 2-way 쌍이 최소 1개 유저스토리에 등장하는지 확인. 미커버 쌍은 추가
3-d. **제외 근거 테이블 작성**: 제외된 모든 조합의 근거 기록
4. Each-choice 최소 커버: 각 값이 최소 1개 유저스토리에 포함
5. 조합 테이블에 추가: `대상 시트: 유즈케이스, ISTQB 기법: 시나리오테스팅`

#### 영역별 유저스토리 조합 출력 형식
```markdown
### 유저스토리 차원 (이 영역)

#### 사용자 상태
| 차원 | 값 목록 |
|------|--------|

#### 사용자 상황
| 차원 | 값 목록 |
|------|--------|

#### 사용자 행동
| 차원 | 값 목록 |
|------|--------|

#### 유저스토리 조합
| US-ID | 상태 | 상황 | 행동 시퀀스 | 동작 차별성 근거 |
|-------|------|------|-----------|----------------|

#### 조합 하한선 검증
| 지표 | 수치 |
|------|------|
| 3축 전체 값 수 | {N} (상태{a} + 상황{b} + 행동{c}) |
| 하한선 = max(7, ceil(N/3)) | {M}개 |
| 실제 유저스토리 수 | {K}개 |

```

### Step 4-P: 플랫폼 차이 체크

1. code_summary.md에서 플랫폼 특화 파일/로직 스캔
   - iOS 전용: *.swift, WKWebView 관련
   - Android 전용: *.kt, WebView 관련
   - Web/MO Web 전용: 반응형 분기, userAgent 분기
2. 동일 기능에 플랫폼 간 구현 차이 존재 여부 판별
3. 차이 식별 시 "플랫폼 분리 대상" 태깅:
   | 기능 | 플랫폼 차이 내용 | iOS | Android | Web | 대상 시트 |
   |------|----------------|-----|---------|-----|----------|
4. 태깅된 기능은 기능 시트에서 플랫폼 차원 분리하여 조합 행 생성

**기본 규칙 유지**: 차이 없는 기능은 Regression에서만 플랫폼 분리

### Step 5: 조합 테이블 생성
1. 각 영역의 차원들을 **조합**하여 테스트해야 할 항목 나열
2. 교차 분석 발견 항목은 **별도 조합으로 반드시 포함** (리스크 높음인 것은 우선)
3. 조합 축소 규칙 (Pairwise-minimum 기준):
   - **값 5개 이하 차원**: 영역 내 차원 간 All-pairs (Pairwise 2-way) 적용
   - **값 6개 이상 차원**: Each-choice + 리스크 기반 추가. 생략된 쌍은 제외 근거 명시
   - **최소 커버리지 하한선**: 영역별 조합 수 ≥ All-pairs 등가 조합 수의 60%
   - 플랫폼(iOS/Android/Web)은 별도 시트(Regression)에서만 분리, 기능 TC에서는 통합 (단, Step 4-P 태깅 예외)
   - 언어(ko/en 등)는 다국어 관련 기능에서만 분리
4. 조합 축소 투명성 보고 (각 영역 조합 테이블 하단에 추가):
   | 지표 | 수치 |
   |------|------|
   | 차원 수 | {N} |
   | 전수 조합 | {N} |
   | All-pairs 등가 | {N} |
   | 실제 생성 | {N} |
   | 커버리지율 | {N}% |
   | 생략 쌍 수 | {N} |

   생략 쌍 근거 (커버리지율 < 100%인 경우 필수):
   | 생략 쌍 | 제외 근거 (물리적 불가능 / 동작 동일 / 리스크 낮음) |
   |---------|---------------------------------------------------|

   **금지**: 커버리지율 60% 미만 영역은 조합 추가하여 60% 이상으로 보충
5. 각 조합에 대상 시트와 ISTQB 기법을 매핑

### Step 6: 시트별 집계 및 예상 TC 수 산출
1. 조합 테이블의 각 행을 6개 시트 중 하나에 매핑
2. 시트별 매핑 항목 수 집계
3. **TC 수 산정 승수 공식 적용** (`기준_실행단위분해.md` A5 규칙):
   ```
   예상 TC 수 = 조합 행 수 × A1 승수 × A2 승수 × A3 승수

   A1 승수 (원자적 분해) = (3차 카테고리별 예상 TC 수 합계) / (3차 카테고리 수)
   A2 승수 (컨텍스트 복제) = 1 + (공통 기능 TC 비율 × (평균 노출 페이지 수 - 1))
   A3 승수 (플랫폼 분리) = 1 + (플랫폼 UI 분리 대상 비율 × 0.5)
   ```
4. 승수 산정 보고 테이블 출력:
   | 지표 | 수치 |
   |------|------|
   | 조합 테이블 행 수 | {N} |
   | A1 승수 (원자적 분해) | {X} |
   | A2 승수 (컨텍스트 복제) | {Y} |
   | A3 승수 (플랫폼 분리) | {Z} |
   | **예상 TC 수** | **{N × X × Y × Z}** |
5. 검증: 예상 TC 수가 조합 행 수의 **3배 미만**이면 A1~A3 승수 산정을 재검토

## 정확성 보장 규칙 (Accuracy Guard Rules)

AI가 매트릭스·교차분석을 생성/갱신할 때 발생하는 5가지 구조적 오류를 방지합니다.

### R1. 소스 파일 참조 필수 (No Memory-Based Writing)
- 교차 분석 항목(CA-xxx) 또는 매트릭스 조합 행을 **작성하기 전에 반드시 해당 요약 파일을 Read 도구로 열어 원문을 확인**한다
- **기억에 의존한 작성 절대 금지** — "~했던 것 같다", "이전에 본 것으로는"은 허용 불가
- 각 항목에 출처 소스를 명시한다 (예: `confluence_summary L78`, `jira_summary L196`)
- 갱신(갱신 모드) 시에도 기존 파일과 요약 파일을 **모두** 읽은 뒤에만 수정한다

### R2. 모순 검증 (Contradiction Check)
- 새 항목을 추가할 때, **같은 소스 내에서 반대 기술이 있는지** 검색한다
  - 예: "10분 내 복원 가능"이라고 쓰기 전에, 같은 소스에 "대화 내용 소실, 복구 불가"가 있는지 확인
- 모순이 발견되면:
  - (a) 어느 쪽이 해당 기능의 정확한 기술인지 문맥으로 판단하거나
  - (b) 판단 불가 시 **불일치(Discrepancy)** 항목으로 기록한다
- 특히 **동일 기능의 서로 다른 컨텍스트**를 혼동하지 않도록 주의한다

### R3. 원문 표현 유지 (Verbatim Preservation)
- 소스에 명시된 **기술 용어, 기능명, 열거형 값, 필드명**은 원문 그대로 사용한다
- 기대결과 작성 시 소스 원문의 표현을 유지한다. 동의어 치환은 의미 변형의 원인이 된다
- 원문이 한국어이면 한국어를, 영문 코드값이면 영문을 그대로 사용한다

### R4. 열거 완전성 검증 (Enumeration Completeness)
- 소스에 **"N종", "N개", "N가지"** 등 수량이 명시된 항목은:
  1. 해당 항목을 **개별적으로 1건씩 나열**한다
  2. 나열 후 **개수를 세어 소스의 명시 수량과 일치하는지 확인**한다
  3. 불일치 시 소스를 재확인하여 누락 항목을 보충한다

### R5. 하위 항목 전개 (Sub-item Expansion)
- 소스에서 하나의 기능이 **2개 이상의 하위 조건/상태/값**을 가지면, 각 하위 항목을 **별도의 행**으로 전개한다
- "대표 1개만 쓰고 나머지 생략"은 **매트릭스 수준에서도 금지**한다
- 단일 행에 콤마로 여러 값을 나열하는 것은 '차원 값 목록'에서만 허용하고, '조합 테이블 행'에서는 각 값이 별도 행이어야 한다

## 주의사항

- **핵심 원칙: 교차 분석은 순수 추가(additive)만 한다**
  - 교차 분석 결과로 기존 TC를 요약·축소·통합해서는 **절대 안 됨**
  - 각 소스에서 개별적으로 도출된 TC는 그대로 유지하고, 교차 분석 발견 항목은 **추가 TC로만** 반영
  - "이미 비슷한 TC가 있으니 교차 분석 TC는 생략" — 이런 판단 금지
- **교차 분석 TC는 별도 시트를 만들지 않는다**
  - 교차 분석으로 추가되는 TC는 성격에 맞는 기존 시트(명세기반, 예외사항, 유즈케이스, 코드영향도, Regression)에 분배
  - 예: 기획↔UI 불일치로 나온 검증 TC → 명세기반, 기획↔코드 누락으로 나온 에러 TC → 예외사항
- 교차 분석은 **불일치 자체를 결함으로 단정하지 않음** — "검증이 필요한 항목"으로 기록
- 매트릭스는 **TC 자체가 아니라 TC가 커버해야 할 조합의 목록**입니다
- 조합 폭발을 방지하되, 리스크가 높은 조합과 교차 분석 발견 항목은 반드시 포함합니다
- 사용자가 매트릭스를 확인하고 영역/차원을 조정할 수 있도록 명확하게 작성합니다
- 매트릭스 완성 후 사용자에게 검토를 요청하고, 승인 후 `/TC생성`으로 진행합니다
