# /TC리뷰 - 테스트케이스 리뷰 및 커버리지 개선

리뷰 대상: $ARGUMENTS
(예: {{프로젝트명}}_테스트케이스_v1.xlsx, 또는 latest)

## 리뷰 관점 (6단계)

### 1단계: 매트릭스 대비 커버리지 검증
- `_summaries/coverage_matrix.md`가 존재하면 **매트릭스 기반 검증** 수행:
  - 매트릭스 조합 테이블의 각 행과 기존 TC를 **1:1 대조**
  - 매트릭스 조합 커버리지율 산출: `(TC가 존재하는 조합 수) / (총 조합 수) × 100%`
  - 커버되지 않은 조합 목록을 시트별로 분류
  - 시트별 매트릭스 목표 대비 실제 TC 수 비교
- `_summaries/cross_analysis.md`가 존재하면 **교차 분석 반영 검증** 수행:
  - 교차 분석 발견 항목(불일치·누락·추가) 중 리스크 높음/중간이 TC에 반영되었는지 확인
  - 교차 분석 기반 TC가 성격에 맞는 기존 시트에 올바르게 분배되었는지 확인
- 매트릭스가 없으면 기존 방식으로 폴백:
  - `_summaries/` 요약 파일과 기존 TC를 대조
  - 요약에는 있으나 TC에 빠진 기능/시나리오 식별
  - 시트별 커버리지 비율 산출

### 1.5단계: 역방향 추적 검증 + 표본 감사

#### 1.5-1. 역방향 검증 (Summary → Matrix)
- 4개 요약 파일의 "테스트 차원 열거" 모든 행이 매트릭스에 대응하는지 확인
- 대응 없는 행 = 매트릭스 누락 후보
- 완전성 앵커 합계와 매트릭스 차원 행 수 비교

#### 1.5-2. 무작위 표본 감사 (10%)
- 전체 TC의 10% (최소 5개, 최대 20개) 무작위 선정
- 각 시트에서 최소 1개 포함
- 역추적 체인: TC → 매트릭스 ID → 요약 항목 → 원본 소스
- 체인 끊김 TC 식별 및 수정 대상 표시

#### 1.5-3. 정량 메트릭 보고
| 메트릭 | 값 | 이상 기준 |
|--------|---|----------|
| TC/매트릭스 행 비율 | {N} | 0.8 미만 = 과소, 2.0 초과 = 과다 |
| 영역 간 편차 | {N} | 평균의 2배 초과 = 불균형 |
| 기대결과 평균 문자 수 (전반 vs 후반) | {N} vs {M} | 후반부가 전반부의 70% 미만 = 품질 저하 |

#### 1.5-4. 보고 형식
```
### 1.5단계 결과: 역방향 추적 검증
- 역방향 검증: 요약 차원 {N}행 중 매트릭스 대응 {M}행 ({X}%)
- 표본 감사: {K}개 TC 역추적 → 체인 끊김 {J}건
- 정량 메트릭 이상: {있음/없음} — {이상 내용}
- 수정 필요 TC: {목록}
```

### 2단계: 시트 간 정상↔에러 대칭 리뷰
명세기반·유즈케이스의 정상 동작 TC에 대응하는 예외사항 TC가 빠짐없이 존재하는지 교차 검토합니다.

#### 2-1. 명세기반 → 예외사항 대칭
- 명세기반 TC를 **기능 영역별로 그룹화** (진입구, 대화, 넥스트액션, 문의등록, 문의내역 등)
- 각 기능 영역의 정상 동작에 대응하는 **실패/에러/예외 TC**가 예외사항 시트에 존재하는지 확인
- 대응 예외가 없는 기능을 누락 갭으로 식별

#### 2-2. 유즈케이스 → 예외사항 대칭
- 유즈케이스의 각 E2E 여정에 대해 **여정 중 예외 시나리오**(네트워크 끊김, API 실패, 상태 불일치 등)가 예외사항 시트에 존재하는지 확인
- 여정의 각 전이 지점(화면 전환, API 호출, 상태 변경)마다 실패 가능성을 검토

#### 2-3. 대칭 리뷰 판정 기준
- **갭 판정**: 명세기반/유즈케이스에 정상 TC가 있으나 예외사항에 대응 TC가 없는 경우
- **커버 판정**: 범용 예외 TC(네트워크 끊김, 서버 500 등)로 간접 커버되는 경우는 커버로 인정
- **리스크 분류**: 높음(사용자 데이터 유실 가능), 중간(기능 중단), 낮음(UI 불편)

#### 2-4. 불필요한 교차 쌍 (수행하지 않음)
아래 방향은 ROI가 낮아 프레임워크 규칙에서 **제외**합니다:
- 예외사항 → 명세기반 (역방향: 예외가 있으면 정상은 반드시 존재)
- 유즈케이스 → 명세기반 (여정의 개별 단계는 이미 명세기반에 존재)
- Regression ↔ 나머지 (Regression은 프로젝트 범위 밖 독립 기능)
- 코드영향도 → 명세기반 (코드 지식 TC를 사용자 관점으로 재작성 불필요)

### 2.5단계: 실행 단위 분해 규칙 준수 검증 (A1~A5)

`기준_실행단위분해.md`의 5가지 규칙이 TC에 올바르게 적용되었는지 검증합니다.

#### 2.5-1. 원자적 분해 검증 (A1)
- 전체 TC의 기대결과를 스캔하여 "~확인" 동사가 **2개 이상**인 TC 식별
- 실행절차에 독립된 행위가 2개 이상이고 각각 다른 결과를 확인하는 TC 식별
- 발견 시 분리 권장 TC 목록으로 보고

#### 2.5-2. 컨텍스트 복제 검증 (A2)
- 매트릭스의 "컨텍스트 복제 목록"과 실제 TC를 대조
- 공통 기능(댓글, 공유, 팔로우 등)이 모든 노출 컨텍스트에서 개별 TC로 존재하는지 확인
- "위와 동일" 형태의 축약 TC가 없는지 확인
- 컨텍스트 복제 커버리지 = (실제 복제된 TC 세트 수) / (매트릭스 목표 세트 수) × 100%

#### 2.5-3. 플랫폼 UI 분리 검증 (A3)
- 매트릭스의 "플랫폼 UI 분리 대상"과 실제 TC를 대조
- PC/Mobile 간 UI 차이가 있는 기능이 플랫폼별 별도 TC로 존재하는지 확인
- 사전조건에 "Only PC" 또는 "Only Mobile"이 명시되었는지 확인

#### 2.5-4. 카테고리 트리 커버리지 검증 (A4)
- 매트릭스의 3단계 카테고리 트리(1차→2차→3차)와 실제 TC를 1:1 대조
- 3차 카테고리 중 TC가 0개인 항목 식별 → 누락 TC
- 카테고리 커버리지 = (TC가 존재하는 3차 항목 수) / (전체 3차 항목 수) × 100%

#### 2.5-5. TC 수 승수 검증 (A5)
- 매트릭스의 승수 공식 예상 TC 수와 실제 TC 수 비교
- 달성율 = (실제 TC 수) / (승수 공식 예상 TC 수) × 100%
- 80% 미만이면 어떤 승수(A1/A2/A3) 적용이 부족한지 분석

#### 2.5-6. 보고 형식
```
### 2.5단계 결과: 실행 단위 분해 검증

| 규칙 | 검증 항목 | 결과 | 비고 |
|------|----------|------|------|
| A1 | 복합 검증 포인트 TC 수 | {N}건 분리 필요 | |
| A2 | 컨텍스트 복제 커버리지 | {N}% | 누락 {M}건 |
| A3 | 플랫폼 UI 분리 커버리지 | {N}% | 누락 {M}건 |
| A4 | 카테고리 트리 커버리지 | {N}% | 빈 3차 항목 {M}개 |
| A5 | 승수 공식 달성율 | {N}% | 예상 {X}개 vs 실제 {Y}개 |
```

### 3단계: ISTQB 기법 적용 검증
- 동치 분할: 입력 데이터의 유효/무효 클래스가 모두 커버되었는지
- 경계값 분석: 경계 조건이 테스트되는지
- 상태 전이: 상태 전이가 모두 커버되는지
- 조건 기반: 복합 조건 조합이 충분한지
- 결정 테이블: 다중 조건 조합의 결과가 결정 테이블로 검증되었는지
- 시나리오 테스팅: 엔드투엔드 사용자 시나리오가 충분한지
- 결함 분류법: 과거 유사 프로젝트의 결함 패턴이 TC에 반영되었는지
- **매트릭스 기법 매핑 교차 검증**: 매트릭스에서 지정한 ISTQB 기법이 해당 TC의 비고란에 실제로 적용되었는지 확인

### 4단계: 플랫폼 교차 검증
- iOS / Android / Web 각 플랫폼별 TC 존재 여부 확인
- 플랫폼 특화 동작(웹뷰 인터페이스, 스와이프 등) 커버 여부

### 5단계: 예외/엣지케이스 점검
- 네트워크 오류, 타임아웃
- 동시 접속, 세션 만료
- 비정상 입력(특수문자, 초장문, 빈값)
- 다국어(ko/en/ja/zh) 전환 시나리오
