# /소스분석 - Phase 1: 소스별 분석 및 요약 생성

분석할 소스를 선택하세요: $ARGUMENTS
(예: confluence, jira, figma, code, all)

## 실행 규칙

1. `설정_소스경로.md`의 소스 URL과 분석 규칙을 참조할 것
2. 분석 결과는 `_summaries/` 폴더에 저장
3. 서술형은 간결하게, 열거형 항목(입력값, 분기, 상태)은 빠짐없이 나열
4. 테스트 관점에서 중요한 정보 위주로 추출

## 소스별 분석 방법

### confluence
- Atlassian MCP(`mcp__atlassian__confluence_get_page`)를 사용하여 페이지 분석
- 펼치기 UI 내 콘텐츠, 순서도 분기, 연결된 하위 페이지 모두 분석
- 젠데스크 웹 관련 내용은 제외
- 결과 저장: `_summaries/confluence_summary.md`

### jira
- Atlassian MCP(`mcp__atlassian__jira_get_issue`)를 사용하여 이슈 분석
- Epic과 하위 Task 모두 분석
- 연결된 GitHub PR도 확인
- 결과 저장: `_summaries/jira_summary.md`

### figma
- Figma MCP(`mcp__figma__get_design_context`)를 사용하여 디자인 분석
- 이미지/색상 무시, 입력/버튼/검증/화면전환만 추출
- 플로우차트 텍스트 → 분기 커버리지 고려
- AS-IS/TO-BE 차이점 비교
- 결과 저장: `_summaries/figma_summary.md`

### code
- GitHub MCP(`mcp__github__get_pull_request_files`)를 사용하여 PR 분석
- CLAUDE.md의 소스 URL 섹션에 명시된 로컬 코드 경로도 함께 분석
- 결과 저장: `_summaries/code_summary.md`

### all
- 위 4가지를 서브에이전트(Task tool)로 **병렬 실행**
- 각 소스를 별도 서브에이전트에게 할당하여 동시 분석
- 모든 분석 완료 후 `_summaries/` 폴더에 4개 요약 파일 생성

## 요약 파일 템플릿
가이드_워크플로우.md의 "요약 파일 템플릿" 섹션을 참고하여 작성할 것.
**필수**: 각 요약 파일 하단에 "테스트 차원 열거" 섹션을 반드시 포함할 것 (입력값, 분기 조건, 상태 열거).

## UI 구조 추출 (카테고리 트리 준비)

Phase 1.5에서 3단계 카테고리 트리(`기준_실행단위분해.md` A4)를 작성할 수 있도록, 소스 분석 시 다음 정보를 추출합니다:

### Figma 분석 시 추가 추출 항목
- **화면 탭/섹션 구조**: 페이지 내 주요 탭(예: Story, Rewards, News, Community)과 각 탭 하위 영역
- **PC vs Mobile 레이아웃 차이**: 같은 기능이 PC/Mobile에서 다른 UI 구성을 가지는지 식별 (A3 준비)
- **공통 컴포넌트 노출 위치**: 댓글, 공유, 팔로우 등 공통 기능이 어느 화면에 노출되는지 (A2 준비)

### Confluence 분석 시 추가 추출 항목
- **기능 분류 체계**: 기획서의 기능 카테고리 계층 (대분류→중분류→소분류)
- **공통 기능 정의**: 여러 페이지에서 공유되는 기능의 명세

### 요약 파일에 추가할 섹션
```markdown
### UI 구조 (카테고리 트리 준비)

#### 화면 구조
| 탭/섹션 | 하위 영역 | 세부 항목 |
|---------|----------|----------|

#### 공통 기능 노출 위치
| 기능 | 노출 페이지/화면 |
|------|----------------|

#### PC/Mobile UI 차이
| 영역 | PC 구성 | Mobile 구성 |
|------|--------|------------|
```

## 완전성 앵커 및 역검증

### 요약 파일 완전성 앵커 필수
각 요약 파일 최하단에 "완전성 앵커" 테이블을 작성한다.

| 항목 유형 | 개수 | 원본 섹션 참조 |
|-----------|------|---------------|
| 입력 필드 | {N}개 | {원본 소스의 해당 섹션/페이지} |
| 분기 조건 | {N}개 | |
| 상태 전이 | {N}개 | |
| 에러/예외 케이스 | {N}개 | |
| 사용자 인터랙션 | {N}개 | |
| **합계** | **{N}개** | |

작성 규칙:
- 각 항목은 요약 본문의 해당 열거 테이블과 1:1 대응 ("입력 필드 12개" 선언 → 입력값 열거 테이블에 12행)
- 원본 섹션 참조에 소스의 구체적 위치(페이지 제목, 섹션명) 기록

### 역검증 절차 (소스분석 완료 직전 수행)
1. 원본 소스의 주요 섹션을 **재열람**(Re-read)한다
2. 완전성 앵커 항목별 개수와 본문 열거 테이블 행 수가 일치하는지 확인
3. 불일치 시 누락 항목을 요약에 추가하고 앵커 수치 보정
4. 역검증 결과를 요약 파일 하단에 기록:
   - 역검증 수행일, 재열람 섹션, 불일치 보정 여부

## 완료 기준
- 각 요약 파일에 테스트 관점의 핵심 정보가 포함되어 있을 것
- 기능 요구사항, 예외 케이스, 영향 범위가 명확히 기술되어 있을 것
- 각 요약 파일 하단에 완전성 앵커 테이블이 작성되어 있을 것
- 역검증 절차가 수행되어 앵커 수치와 본문 열거 행 수가 일치할 것
